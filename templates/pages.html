Pipeline inventory (CycloneDX) glsec inventory

Not a findings report: glsec inventory .gitlab-ci.yml > pipeline.cdx.json writes a CycloneDX 1.6 BOM of the images, services and includes a pipeline pulls in. Upload it to Dependency-Track or another CycloneDX tool, and the pipeline is tracked next to your application's dependencies. Every component carries a glsec:pinning property, so you can filter for references that aren't pinned: mutable, none or unresolved.

glsec {{$.Version}} lists these components. The BOM around them also has the pipeline file as metadata.component and a dependencies entry that links it to each component.

Components
{{.Components}}
  • It works offline and isn't transitive: includes are listed, not fetched, so what an include brings in itself is not in the BOM.
  • local: and artifact: includes are left out, since they come from the repository or the pipeline.
  • There is no vulnerability data; the SBOM tool adds it from the purls.
  • The output is deterministic: no timestamp, and the serial number is derived from the content, so an unchanged pipeline gives the same BOM.

All properties and what each glsec:pinning value means: pipeline inventory in glsec's docs.

Performance

{{with .Perf}}

How long glsec takes to scan one large pipeline: 2,000 jobs with extends: and !reference chains, anchors and long scripts, about 650 KB, far bigger than real pipelines so that slow code shows. Every release since v{{.Start}} and every change to main is measured on the same file, each time as the median of seven runs. Every dot links to its commit; hover for the details.

The time grows with the rules: each release checks more{{if .First.Rules}}, from {{.First.Rules}} rules in {{.First.Label}} to {{.Latest.Rules}} in {{.Latest.Label}}{{end}}. The releases were measured one after another on the same machine, so their times compare.
